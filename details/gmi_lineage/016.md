# Operating rules for future assistants

1. Read `coverage.json`, `manifest.json`, and `maintenance/documentation_progress.md` first. Never interpret lexical indexing as complete semantic or runtime verification.
2. Use only the sanitized deployment lookup files and bounded text ranges. Stale or missing evidence is unresolved; never fetch the original repository.
3. Keep source/data read-only for documentation tasks. Do not execute production scripts, fetch data, install commands, or overwrite datasets without explicit authorization. Documentation maintenance writes only inside `AI_KNOWLEDGE/`.
4. Distinguish current, archive, and QA namespaces. Same variable name across loads is not identity. Resolve the dataset context before following edges. All graph statuses and relationship types matter; `INFERRED` edges are candidate effects, not proof.

## Variable questions

Resolve the variable semantic ID through lookup/ids and lookup/edges. Identify file, load context and source dataset; retain ordered transformations and evidence status. Use bounded sanitized excerpts for ambiguous macros or merges. Missing schemas remain unresolved; do not retrieve originals.

## Indicator questions

Locate current or archived indicator record. Retrieve its exact expression, expansion parameters, original template, sample guards, weight selection and aggregation invocation. Read the referenced blocks and all upstream sample filters. Check `reference_period_scope`: AGNOSTIC for labor recall is not calendar, PPP or spell independence. Trace formatting and final output fields; a field may be renamed or intentionally dropped. For external commands, report the precise invocation and return-matrix mapping and say the internal formula is unavailable; do not replace it with a textbook formula.

## Error questions

Start at the affected output/variable and producer block. Read preceding guards and immediate input paths. Trace inputs upstream. Consult `findings.jsonl` and merge/append audit. List source-supported failure candidates and the exact next inspection, never a hypothetical cause as confirmed. Prioritize unset resume globals, actual runner filenames, unguarded formatter drops/labels, merge uniqueness, absent files and external commands. An uncaptured failing statement can prevent later outputs.

## Modification impact

Use lookup/edges for the entity and follow every adjacency part with its evidence status. Separate formula, sample/grouping, file and imported-data effects. These are direct recorded edges; a bounded impact set is not proof of numerical effects.

## Evidence vocabulary

- `VERIFIED_STATIC`: source statement/explicit transformation established by inspection.
- `VERIFIED_RUNTIME`: authorized execution or data inspection only; this release has none.
- `INFERRED`: candidate or conditional semantic/dataflow relationship requiring confirmation.
- `UNVERIFIED`: not established from the available material.
- `EXTERNAL_DEPENDENCY`: absent input, implementation, environment, or service.

Source comments claiming prior runtime tests remain author-reported comments, not VERIFIED_RUNTIME evidence.

## Response format

**Answer:** Direct response.

**How it works:** Relevant formula, guards, weight and aggregation.

**Lineage:** Input → transformations → indicator → final field/output.

**Evidence:** Exact source files and line ranges.

**Uncertainty:** External implementations/data, unresolved dynamic behavior and any stale references.

Keep the response short; link the fuller record. Report incomplete coverage plainly. Proposed root-level instructions are in `maintenance/proposed_AGENTS_addition.md`; do not modify repository instructions automatically.
