# How to answer

For any AI assistant reading this repository. Follow this whenever you answer a
question using these documents.

## Keep the answer short

- Bullet points, not paragraphs.
- Plain English. Short sentences. No jargon unless the user used it first.
- If you must use a technical term, say what it means in a few words.
- Aim for under 150 words unless the user asks for more.

## Use this shape

1. **What your code does** - in one or two bullets.
2. **What the package or dashboard expects** - in one or two bullets.
3. **What I think is going on** - your best reading, said as a guess, not a verdict.
4. **What to try** - one concrete change.

End with: "If that does not fix it, contact the PEA team."

## Rules

- Never tell the user to go read the product source code. They usually cannot.
- Never invent a parameter, option, variable or behaviour that is not written in
  these documents.
- If the documents do not answer the question, say plainly that it is not recorded
  here and tell them to contact the PEA team. That is a good answer, not a failure.
- If a document marks something `INFERRED` or `UNVERIFIED`, do not state it as
  settled. Say it looks likely and should be checked.
- A document describes what the code does. It does not prove what happened in a
  particular country-year run.

## Common user mistakes to check first

When a user shares code and an error, check these before anything else:

- A parameter passed that the command does not accept, or a required one missing.
- The wrong one of two similar parameters, for example a benchmark option used
  where a group option was meant, or the reverse.
- A variable passed raw when the command expects one that was built first.
- A poverty line, PPP year or welfare type that does not match the data loaded.

# Shared conventions

Every folder in this repository follows these conventions so that documents from different products can be read together and compared. The vocabulary originates in `AI_KNOWLEDGE/` of `dasalm20/gmi_extended`; keep it identical rather than inventing per-product variants.

## Evidence vocabulary

Every claim carries one of these. Never upgrade a claim when restating it.

| Tag | Meaning |
|---|---|
| `VERIFIED_STATIC` | The source code demonstrably does this. Does not establish any observed data value. |
| `INFERRED` | A conditional finding from static analysis. Holds if the stated conditions hold. |
| `UNVERIFIED` | Named but unresolved from the analysed snapshot. |
| `EXTERNAL_DEPENDENCY` | Lives outside the analysed repository: questionnaires, upstream harmonisation, user-written commands, input data. |
| `RUNTIME_CONFIRMED` | Someone ran it and recorded the result, with date, inputs and command. *(Proposed addition, not yet in the GMI base. Drop it if you would rather keep the vocabulary frozen.)* |

Coverage of any folder is `PARTIAL_STATIC` unless its README says otherwise: source behaviour is documented, statistical results are not.

## Citations

Cite as `path/from/repo/root/file.do:Lnnn-Lnnn`, copied verbatim from the index record, never retyped from memory. A citation proves source behaviour or invocation, not successful execution or an observed value.

For a product whose source lives in another repository, state the repository and the commit the analysis was made against, so a citation stays meaningful after upstream changes.

## Folder layout

Each product folder follows the same spine:

```
<Product>/
  README.md        what this product is, what it consumes, what it produces, where to start
  ANSWERS.md       questions as consumers actually phrase them, each with answer + citation + link
  analysis/        cross-cutting findings
  architecture/    execution and data flow
  variables/       per-variable records
  indicators/      per-indicator or per-output-cell records, plus INDEX.md
  index/           machine-readable records (.jsonl)
  schemas/         record schema and evidence vocabulary
  maintenance/     progress, unresolved questions, validators
```

A product that is analysed differently can omit folders, but must say so in its README rather than leaving an empty directory.

## Identity rule

Same-named fields in different products, different files, or different load contexts are **separate identities** until a crosswalk row says otherwise. Do not merge them.

## Honesty rules

1. An absent or skeleton document means *not analysed*. It never means *nothing to report*.
2. Do not state a data value this repository has not recorded.
3. When a question needs runtime evidence, give the exact check rather than guessing the result.

## Which folder answers your question

Match the question's **shape**, not its vocabulary.

| If the question is… | Start here | Then |
|---|---|---|
| How does one product compute something, or why did one product fail | that product's folder | stop, unless the answer cites another product |
| Two products give different numbers for the same indicator | **PEA_interaction/** | then both product folders, for the two definitions |
| A cell is blank in one product but populated in another | **PEA_interaction/** | then both product folders |
| Where does a number come from / what feeds what | **PEA_interaction/** | then the producing product |
| Changing something in one product, want to know what else breaks | **PEA_interaction/** | then every consumer it names |
| You cannot tell which product the question is about | **PEA_interaction/README.md** ownership table | then the product it points to |

### Worked examples

- "Why does `pea_tableC1` error with r(459) on `aggregate(groups)`?" → one product. `Stata_package/`.
- "Does GMI distinguish 7-day from 12-month labour reference periods?" → one product. `GMI_extended/`.
- "The dashboard shows [ESTIMATE] in agriculture but my Stata run gives [ESTIMATE]." → two products. `PEA_interaction/` first. Answering this from either product folder alone produces a wrong answer, because each is internally correct.
- "The 2018 labour rows are blank in the PEA table but the dashboard has them." → two products. `PEA_interaction/` first.

## Stop rules

1. **Never answer a two-product question from one product's folder.** Each product can be internally consistent and still disagree with its neighbour. The disagreement lives in `PEA_interaction/`, nowhere else.
2. **Never assume two same-named fields are the same concept.** `_industry_ind1` in GMI and `_agriculture` in the Stata package both mean "share in agriculture" and are computed over different samples from differently coalesced inputs. Check [PEA_interaction/crosswalk.md](../cross_product/0001.md#L203-L220).
3. **Source behaviour is not a data result.** These documents describe what the code does. Whether a given mechanism fired for a given country-year is a separate question, answered by running the checks each document provides, not by reading.
4. **Respect the evidence vocabulary.** See [CONVENTIONS.md](0001.md#L62-L125). Do not restate an `INFERRED` or `UNVERIFIED` finding as settled.
5. **Answer from this help center.** It holds what is known about the three products. Citations name a source line for provenance; they are not an instruction to open the product repositories, and most readers cannot.
6. **When the answer is not here, say so and stop.** Do not guess, and do not send the reader to the source. Tell them to contact the PEA team.
